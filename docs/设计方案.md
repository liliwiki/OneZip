# OneZip 设计方案（v0.1 草案）

> 目标：一款 Windows 一体化压缩管理工具，融合
> **NanaZip**（现代 Windows 外壳 + 7-Zip 级格式兼容 + 常规压缩）、
> **HatchZip**（本地"边解压边释放原档空间"、可断点恢复）、
> **Peel**（边下载边解压、并行分段下载、打洞保持磁盘占用平稳、可续传）
> 三者核心能力，统一 GUI 与右键菜单。
>
> 项目名 OneZip 为暂定名，可随时更换。

---

## 0. 已定决策（2026-11-25）

- **走方案 C**：自研统一引擎，上游按"库"复用，不做外壳式调度，也不做源码大合并。
- 核实后，HatchZip 和 Peel 都是 Rust、MIT OR Apache-2.0、支持 Windows，且都已拆成库：
  - 本地边解边删 → 直接依赖 **`hatchzip-core`**（crates.io，固定 `=0.1.10`）。
  - 边下边解 → 直接依赖 **`peel-rs`**（未发布到 crates.io，git 固定到 agouin/peel v0.8.0 提交）。
  - 因此下文第 3、4 节描述的算法由上游提供，OneZip 负责统一入口、统一事件、前端与两者之间的衔接；
    上游修复通过升级版本获取，不在本仓库维护其源码副本。
- 7z.dll（NanaZip/7-Zip）用于补齐 iso/wim/cab 等格式与常规压缩，排在后续里程碑。
- 当前代码：`crates/onezip-core`（`extract()` 按来源分流到两个引擎）、`crates/onezip-cli`（`onezip x`）。

## 2. 总体架构

```
┌──────────────────────── 用户入口 ────────────────────────┐
│  OneZip.App (WinUI 3)   OneZip.Shell (IExplorerCommand)  │
│  onezip.exe (CLI)       拖拽 / 文件关联 / 协议 onezip:// │
└───────────────┬───────────────────────────┬──────────────┘
                │ 命名管道 JSON-RPC（本机、按用户 ACL）  │
┌───────────────▼───────────────────────────▼──────────────┐
│ onezipd.exe  任务守护进程（每用户一个，按需启动、空闲退出）│
│  ├ 任务队列/调度（并发度、IO 优先级、暂停/恢复/取消）    │
│  ├ 任务日志 Journal（WAL，断点恢复的唯一事实来源）       │
│  └ 进度/事件推送                                          │
└───────────────┬──────────────────────────────────────────┘
                │ 进程内调用
┌───────────────▼──────────────────────────────────────────┐
│ onezip-core（Rust 库）                                    │
│  ├ source  : LocalFile / Http(Range, 并行) / MultiVolume  │
│  ├ planner : 根据格式与模式生成"提取计划"(顺序/逆序/按块)│
│  ├ format  : 原生流式读取器(zip/tar/gz/zst/xz/lz4/bz2)    │
│  │           + 7z.dll 桥接(7z/rar/iso/wim/cab/… 全格式)  │
│  ├ sink    : 安全写出(临时文件→校验→原子改名)、路径净化 │
│  ├ reclaim : 空间回收(尾部截断 / NTFS 稀疏打洞 / 删分卷)  │
│  └ journal : 检查点、条目状态机、崩溃恢复                 │
└──────────────────────────────────────────────────────────┘
```

### 2.1 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 核心引擎 | **Rust** | 内存安全（解析不可信压缩包）、tokio 异步下载、现成 crate：`zip`/`tar`/`flate2`/`zstd`/`xz2`/`lz4_flex`/`bzip2`/`reqwest`；HatchZip、Peel 同类实现也以 Rust 为主 |
| 全格式兼容 | **7z.dll（NanaZip 或 7-Zip 构建）** 动态加载，通过 `IInArchive/IOutArchive` COM 接口桥接 | 一次获得 7-Zip 全部格式；动态链接满足 LGPL；自定义 `IInStream/ISequentialOutStream` 即可接入回收与下载逻辑 |
| 守护进程 | Rust 可执行文件 | 与 core 同语言，零 FFI |
| GUI | **WinUI 3 + C#/.NET 8**（Windows App SDK） | 原生 Win11 风格、深色模式、Mica；与 daemon 走 IPC，GUI 崩溃不影响任务 |
| 右键菜单 | **C++/WinRT**，`IExplorerCommand` + 稀疏 MSIX 包（Win11 一级菜单）；Win10 回退经典 `IContextMenu` | NanaZip 同款做法；Explorer 进程内 DLL 必须轻量，只负责发 IPC |
| 打包 | MSIX（商店/侧载）+ 便携 zip | 稀疏包让非商店安装也能注册 Win11 菜单 |
| 构建 | 全部在 Windows 机上：`cargo`（MSVC 目标）、MSBuild/Visual Studio 2022、Windows SDK | Linux 机只写代码 |

### 2.2 进程模型的理由
- Explorer 右键 → Shell DLL 只把"动作+路径"发给 daemon，避免 Explorer 卡死/崩溃。
- 多个右键操作汇聚到同一任务队列，可统一限流（避免 8 个解压同时打满磁盘）。
- GUI 关闭任务继续；daemon 被杀/断电后，下次启动读取 Journal 自动提示恢复。

## 3. 核心难点一：本地边解压边删除（HatchZip 式）

### 3.1 原理
文件系统只能高效地 **从尾部截断**（`SetEndOfFile`，任何文件系统可用），或在 NTFS/ReFS 上把文件标记为稀疏后 **在任意位置打洞**（`FSCTL_SET_SPARSE` + `FSCTL_SET_ZERO_DATA`，真正归还簇）。据此有三种回收策略，planner 按格式和卷类型自动选择：

| 策略 | 做法 | 适用 | 文件系统要求 |
|---|---|---|---|
| **R1 逆序截断** | 先把索引（ZIP 中央目录 / 7z 尾部头）复制到 Journal；按数据偏移从大到小提取条目，每个条目落盘并校验后把原档截断到该条目起始偏移 | ZIP（含 Zip64）、非固实 7z、按块的固实 7z、ISO 等"有索引 + 随机访问"格式 | 任意（含 exFAT/FAT32） |
| **R2 顺序打洞** | 前向流式解码，已被解码器完全消费且已过检查点的区间打洞 | tar.gz/xz/zst/bz2/lz4、固实 RAR、无法随机访问的流 | NTFS / ReFS |
| **R3 整卷删除** | 分卷包按卷消费，某卷所有数据均已提交则删除该卷 | .7z.001、.partN.rar、.z01… | 任意 |

R1/R2 可与 R3 叠加（分卷内部再截断/打洞）。

### 3.2 峰值额外空间
- ZIP / 非固实 7z：≈ 最大单个条目的（压缩大小 + 解压大小）。
- 固实 7z：≈ 最大一个固实块（folder）的解压大小——**这是硬限制**，必须在开始前计算并告知用户；可提示"该包固实块 40 GB，需要至少 40 GB 空闲"。
- 流式格式：≈ 解码器窗口 + 当前写出文件 + 未到检查点的压缩数据。

开始前做 **空间预算**：`需要的峰值 ≤ 可用空间 − 安全余量(默认 1 GB)`，不满足则拒绝或建议换策略。

### 3.3 安全流程（每个条目的状态机）

```
PENDING → WRITING(临时文件 .onezip.part) → WRITTEN(CRC/哈希校验通过)
        → FLUSHED(FlushFileBuffers + 原子改名为最终名)
        → JOURNALED(Journal 记录 committed 并 fsync)
        → RECLAIMED(截断/打洞/删卷，Journal 再记录 reclaimed 并 fsync)
```

铁律：**源数据只有在"其对应输出已持久化且已校验、Journal 已落盘"之后才能释放。** 任何时刻断电，恢复时：
- `RECLAIMED` 之前的条目：源数据仍在，可重做；
- `RECLAIMED` 之后的条目：输出文件已持久化，跳过；
- 半写的 `.onezip.part`：删除重做。

额外保护：
1. **破坏性操作前强制预检**：密码验证、索引完整性、（可选、默认开启于"不可重下的文件"）全量 test 一遍 CRC。
2. 原档身份指纹（大小、修改时间、头部/索引哈希）写入 Journal，恢复时不匹配则拒绝继续。
3. 禁用场景：网络盘/UNC、只读介质、OneDrive 占位文件、被其他进程占用的文件（独占打开 `FILE_SHARE_READ` 拒写）。
4. UI 上明确标为"不可逆"，需二次确认；默认模式是普通解压，回收模式需主动选择。
5. Journal 放在目标卷（与输出同卷，保证同一持久化域），路径 `<输出目录>\.onezip\<任务ID>.journal`。

## 4. 核心难点二：边下载边解压边释放空间（Peel 式）

### 4.1 数据流

```
HTTP(S) ──并行 Range 分段──▶ 稀疏暂存文件(.onezip.dl) ──连续前缀──▶ 解码器 ──▶ sink
              ▲                    │已消费且过检查点的区间
              │ 下载位图 bitmap     └──────── 打洞释放 ────────▶ 磁盘占用平稳
              └──── Journal 记录：ETag/Last-Modified、已下载区间、解码检查点
```

- **探测**：HEAD/首个 Range 请求获取长度、`Accept-Ranges`、ETag、Last-Modified、Content-Encoding。
- **格式感知调度**：
  - 流式格式（tar.*）：分段下载器优先填满"解码前沿"之后的窗口（滑动窗口，默认 64–256 MB），不要远超前沿下载，否则失去"占用平稳"的意义。
  - ZIP/7z：先 Range 取尾部（中央目录/尾头），再按条目或固实块顺序调度下载，每块下载完即解，解完即打洞。
  - 不支持 Range 的服务器：退化为单连接顺序流，仍可边下边解，但断点续传只能从头（明确提示）。
- **完整性**：条目 CRC + 可选整体哈希（用户提供 SHA-256 或服务器提供）；ETag 变化则中止并要求重新开始。

### 4.2 断点续传与"已释放数据"的矛盾
打洞后数据就没了，续传时解码器必须能从某个点 **重新开始**。方案：**检查点 = 可重启解码的位置**，打洞只打到最近检查点之前。

| 格式 | 检查点粒度 |
|---|---|
| ZIP / 非固实 7z | 每个条目边界（天然独立） |
| 固实 7z | 每个固实块边界 |
| tar.zst（多帧）/ xz（多块）/ bgzip / pigz --independent | 帧/块边界（天然独立） |
| tar.gz（单 deflate 流） | deflate 块边界 + 保存 32 KB 滑动窗口快照到 Journal |
| tar.bz2 | bzip2 块边界（块独立） |
| 单帧大窗口 zstd / 单块 xz | 无法廉价快照 → 只保留"最近条目边界后"的压缩数据不打洞；最坏情况续传时从该点重新 Range 下载 |

由于源头是远端，最坏情况也只是"多下载一段"，不会丢数据。

### 4.3 网络细节
- 连接数自适应（默认 4–8），单段失败指数退避重试，代理/系统证书走 WinHTTP 设置或 `reqwest` + `rustls-platform-verifier`。
- 支持 Cookie/Header 注入（给浏览器扩展或下载器集成用，v2）。
- 下载文件同样打 MOTW（`Zone.Identifier`，含 HostUrl），并传播到解压出的文件。

## 5. 智能解压

1. **格式嗅探**：按魔数识别，不信扩展名；识别伪装（如 .exe 实为 SFX 7z）。
2. **目录策略**：顶层只有一个目录 → 直接解到当前位置；否则建 `<包名>\`；单文件 → 直接放出。可在设置中改为"总是建目录"。
3. **嵌套拆包**：`.tar.gz` 一步到位；包内只有一个压缩包时询问/自动继续拆（可设深度上限）。
4. **文件名编码**：ZIP 无 UTF-8 标志时用统计检测（GBK/Big5/Shift-JIS/CP437…），预览中可手动改编码。
5. **分卷识别**：从任意一卷进入都能找到全组，缺卷时提前报告缺哪一卷。
6. **密码**：密码本（DPAPI 加密存储）自动尝试；单次任务的密码只在内存中。
7. **冲突策略**：询问/覆盖/跳过/自动重命名/仅当更新时覆盖。
8. **完成后动作**：打开目录、删除原档（进回收站）、关联"回收模式"。

## 6. 数据安全与健壮性清单

- **Zip-Slip / 路径穿越**：拒绝绝对路径、`..`、盘符、ADS（`:`）、设备名（CON/NUL/COM1…），符号链接/联接默认不还原。
- **长路径**：内部统一使用 `\\?\` 前缀；非法字符替换并记录映射。
- **解压炸弹**：压缩比阈值、总输出上限、条目数上限、嵌套深度上限，超限暂停询问。
- **MOTW**：与 NanaZip 一致地传播 Mark-of-the-Web。
- **原子写出**：临时名 → 校验 → 改名；失败不留下半截目标文件。
- **崩溃恢复**：daemon 启动扫描 Journal，GUI 列出"未完成任务"，一键恢复或放弃（放弃时不会再删除任何源数据）。
- **Defender/杀软**：写出后再改名，减少扫描触发次数；不做任何规避。
- **权限**：不需要管理员；不使用 `SetFileValidData`（需特权）。

---

## 7. 性能

- IO 与解码分线程流水线（读 → 解码 → 写），大缓冲（1–4 MB），写出前用 `FileAllocationInfo` 预分配减少碎片。
- 非固实 ZIP/7z 条目级并行解压（回收模式下为保证逆序截断，并行窗口限定在"尾部 N 个条目"）。
- 多线程编解码器：zstd/xz/7z LZMA2 多线程。
- 小文件大量场景：批量创建、延迟设置时间戳/属性。
- 任务调度识别物理磁盘，同盘任务串行、异盘并行；后台任务使用低 IO 优先级。
- 基准对比对象：NanaZip/7-Zip 同包同参数，目标不低于其 95%。

## 8. 格式兼容矩阵（v1 目标）

| 格式 | 读 | 写 | 回收策略 | 边下边解 |
|---|---|---|---|---|
| zip / zip64 | ✓ | ✓ | R1 | ✓（先取尾） |
| 7z 非固实 / 固实 | ✓ | ✓ | R1（按条目/按块） | ✓（按块） |
| rar4 / rar5（含固实） | ✓（7z.dll） | ✗ | R2（NTFS）/ R3 | ✓（顺序） |
| tar / tar.gz / tgz / tar.bz2 / tar.xz / tar.zst / tar.lz4 | ✓ | ✓ | R2 | ✓ |
| gz / bz2 / xz / zst / lz4 / br 单文件 | ✓ | ✓ | R2 | ✓ |
| iso / wim / cab / msi / dmg 等 7z.dll 可读格式 | ✓ | 部分 | R1（有索引者）否则仅普通解压 | 视格式 |
| 分卷（.001 / .partN.rar / .z01） | ✓ | ✓（7z/zip） | + R3 | ✓（多 URL，v2） |

不支持回收的格式会自动回退到"普通解压 + 完成后删原档"，并在 UI 中说明原因。

## 9. 统一交互设计

### 9.1 右键菜单（Win11 一级菜单，单个"OneZip"子菜单）
- 智能解压到此处 / 解压到"<包名>\" / 解压到…
- **解压并释放空间（不可逆）**
- 添加到"<名称>.7z" / "<名称>.zip" / 添加到压缩包…
- 测试压缩包 / 计算哈希
- 选中多个包：批量智能解压

### 9.2 主界面
- 首页：拖拽区 + "从 URL 解压"输入框 + 最近任务。
- 浏览器：像文件夹一样浏览压缩包，预览，选中部分提取。
- 任务中心：进度、速度、**磁盘空间曲线（原档剩余 / 已释放 / 输出增长）**、暂停/恢复/取消、恢复未完成任务。
- 设置：默认策略、安全阈值、密码本、关联、菜单项开关。

### 9.3 CLI（与 GUI 等价，方便脚本与测试）
```
onezip x  <archive|url> [-o dir] [--reclaim auto|off] [--verify full|index]
onezip a  <archive> <files...> [-t 7z|zip|tar.zst] [-mx 0-9] [-v 4g] [-p]
onezip t  <archive>
onezip resume <task-id> | onezip tasks
```

## 12. 测试策略

1. **故障注入（最重要）**：在每个状态迁移点随机 kill daemon / 拔网线 / 模拟写失败，恢复后比对输出哈希与参考解压结果，要求 100% 一致且不丢数据。可在 Hyper-V 虚拟机里做硬断电测试。
2. **格式语料**：各格式 × 固实/非固实 × 加密 × 分卷 × Zip64 × 非 UTF-8 文件名。
3. **模糊测试**：`cargo-fuzz` 覆盖原生解析器；7z.dll 路径用畸形样本回归。
4. **空间断言**：测试中采样卷空闲空间，断言峰值额外占用不超过 planner 预算。
5. **网络**：本地 HTTP 测试服务器模拟无 Range、限速、断流、ETag 变更、返回错误内容。
6. **性能基准**：与 NanaZip/7-Zip 同包对比。

## 13. 里程碑

| 阶段 | 内容 | 产出 |
|---|---|---|
| M0 | 仓库/构建链（Windows 上 cargo + MSBuild）、CI、7z.dll 桥接 PoC | 能用 CLI 列出 7z/rar 内容 |
| M1 | core：普通解压/压缩、智能解压、安全写出、Journal | CLI 可替代日常使用 |
| M2 | 本地回收模式：R1（zip/7z）、R3、空间预算、故障注入测试 | `onezip x --reclaim` |
| M3 | 边下边解：并行 Range、稀疏打洞（R2）、检查点续传 | `onezip x https://…` |
| M4 | daemon + IPC + 任务队列与恢复 | 后台任务 |
| M5 | WinUI 3 GUI + 右键菜单 + MSIX 打包 | 首个可安装版本 |
| M6 | 性能调优、更多格式回收支持、多 URL 分卷、浏览器集成 | v1.0 |

M2/M3 是本项目区别于普通压缩软件的价值所在，建议 M0 之后先做一个"zip 逆序截断"的最小原型，尽早验证安全流程和故障注入框架。
